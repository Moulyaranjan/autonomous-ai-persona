# SignalForge AI — Build Prompt

## Role

You are a senior Python backend engineer and AI systems architect.

Build a production-style autonomous AI technology persona called **SignalForge AI** for the ABTalks Vibe Coding Hackathon.

The system must behave as an autonomous technology analyst rather than a simple chatbot. After an evaluator initializes an agent once, the system should continuously discover technology information, evaluate it against the persona's domain, remember previously processed topics, generate grounded content, publish it, and repeat without requiring further human prompts.

## Core Objective

Build an autonomous AI agent with this lifecycle:

POST /api/agent/init
↓
Create / initialize persona
↓
Start autonomous background scheduler
↓
Discover fresh technology topics
↓
Aggregate multiple sources
↓
Normalize and deduplicate topics
↓
Check agent-specific memory
↓
Evaluate topics editorially
↓
Accept the highest-quality relevant topic
↓
Generate persona-specific content
↓
Persist the post with rationale and sources
↓
Wait for the configured interval
↓
Repeat automatically

The evaluator should only need to initialize the agent once and then observe its feed.

## Required API Contract

### POST /api/agent/init

Request:

```json
{
  "persona": {
    "name": "Ada",
    "domain": "AI Security"
  }
}
```

Response:

```json
{
  "agentId": "uuid"
}
```

Calling this endpoint must start the agent's autonomous background loop.

### GET /api/agent/feed?agentId={agentId}

Return the posts generated by that agent.

Each post should contain:

```json
{
  "id": "uuid",
  "createdAt": "timestamp",
  "text": "generated post",
  "rationale": "why the topic was selected",
  "sources": \[
    "source URL"
  ]
}
```

## Autonomous Topic Discovery

Create a multi-source discovery system.

Use sources such as:

* RSS feeds
* Hacker News
* GitHub Trending
* arXiv

Each source should be isolated so that failure of one source does not stop the complete discovery pipeline.

Use asynchronous execution where appropriate.

Normalize discovered items into a common topic representation.

Each topic should contain:

* title
* description/content
* source
* source URL
* publication time
* relevance metadata

## Topic Processing

After discovery:

1. Normalize all topics.
2. Remove duplicates.
3. Convert source-specific data into a common `TopicCandidate` representation.
4. Ignore invalid or unusable topics.
5. Check whether the agent has already processed the topic.

Do not allow the same agent to repeatedly publish the same topic.

Memory must be isolated per agent.

## Editorial Engine

Create a deterministic editorial evaluation layer.

Score every candidate according to:

* Persona-domain alignment
* AI/technology relevance
* Recency
* Source credibility
* Publishing relevance

Use a configurable acceptance threshold.

Default:

```text
TOPIC\_SCORE\_THRESHOLD=60
```

The editorial engine must return:

* score
* ACCEPT / REJECT decision
* reasoning/rationale

Only accepted topics should proceed to content generation.

If multiple topics are accepted, prioritize the highest-scoring topic.

## Persona Writer

Generate content in the voice of the configured persona.

The generated content must:

* Stay within the persona's domain.
* Be grounded in the discovered topic.
* Avoid inventing statistics.
* Avoid fabricated URLs.
* Avoid unsupported claims.
* Use the provided source information.
* Produce useful technology insight rather than generic AI text.

The writer should receive:

* persona name
* persona domain
* selected topic
* source information
* editorial context

## LLM Architecture

Use an abstraction layer for LLM providers.

Create a provider interface such as:

```python
class LLMProvider(ABC):
    @abstractmethod
    async def generate(self, prompt: str) -> str:
        ...
```

Implement an Ollama provider for local inference.

Default configuration:

```env
OLLAMA\_HOST=http://localhost:11434
OLLAMA\_MODEL=llama3.2:3b
```

The system must gracefully handle LLM unavailability.

If the primary LLM provider fails:

* catch the exception
* log the failure
* use a safe fallback provider
* continue the autonomous loop
* do not crash the agent

## Memory System

Implement persistent agent-specific memory.

Before processing a topic:

```text
Has this agent already seen/published this topic?
```

If yes:

```text
Skip topic
```

If no:

```text
Continue evaluation
```

Memory should prevent duplicate publishing across scheduler cycles.

## Persistence

Use SQLAlchemy with asynchronous database access.

Persist:

### Agents

* id
* name
* domain
* active status
* timestamps

### Posts

* id
* agent ID
* topic information
* generated text
* editorial rationale
* source URLs
* creation timestamp

Use SQLite for the default local development configuration.

Make database configuration environment-driven.

## Autonomous Scheduler

The scheduler must:

* Start after `/api/agent/init`.
* Run continuously in the background.
* Discover and process topics.
* Publish accepted posts.
* Sleep for the configured interval.
* Repeat indefinitely.

Default:

```env
PUBLISH\_INTERVAL\_SECONDS=60
```

Prevent duplicate scheduler tasks for the same agent.

Handle:

* cancellation
* source failures
* LLM failures
* individual cycle failures

A failure in one cycle must not permanently terminate the autonomous agent.

## Application Startup

Use FastAPI lifespan handling.

When the application starts:

1. Initialize database tables if necessary.
2. Find active agents.
3. Resume their autonomous loops.

This allows active agents to continue after application restarts.

## Engineering Principles

Follow these principles throughout implementation:

1. Prefer simple, maintainable solutions over unnecessary complexity.
2. Keep services modular and independently testable.
3. Use async I/O for external/network/database operations.
4. Never allow one external dependency failure to kill the autonomous agent.
5. Never fabricate source URLs or statistics.
6. Keep persona behavior deterministic where possible.
7. Store editorial reasoning so evaluators can understand why a topic was selected.
8. Make the system observable through logs and API responses.
9. Avoid unnecessary dependencies.
10. Do not over-engineer features that are not required by the hackathon specification.

## Final Acceptance Criteria

The implementation is complete when:

* `/api/agent/init` works.
* An agent is created successfully.
* The autonomous scheduler starts automatically.
* Topics are discovered from multiple sources.
* Topics are scored against the persona domain.
* Previously processed topics are skipped.
* An accepted topic generates a persona-specific post.
* The post is persisted.
* The rationale and source URLs are preserved.
* `/api/agent/feed` returns generated posts.
* LLM failures do not kill the autonomous loop.
* Active agents can resume after application restart.
* Tests cover the major workflow.
* Swagger documentation is available.
* The application can be deployed as a FastAPI web service.

Build the complete system, not a mock demo. Prioritize a working end-to-end autonomous pipeline over adding unnecessary features.
